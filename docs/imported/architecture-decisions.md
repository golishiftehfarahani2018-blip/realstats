# تصمیم‌های معماری — ۲۰۲۶/۱۰/۲۶

مرجع مقدم: دستور فعلی مالک محصول. محصول مستقل، بدون هویت یا سیاست ثابت مشتری قبلی است.

| ADR-002 سازمان | Organization → Office → Membership؛ User مستقل است. نقش و وضعیت فعال روی عضویت است. API ساخت دفتر اضافی وجود ندارد. هر نصب یک مشتری دارد. |
| ADR-003 امنیت | نشست Django با HttpOnly، SameSite=Lax، Secure در تولید، CSRF برای ورود و تمام تغییرها. هویت و دفتر از نشست سرور؛ نقش یا معرف ارسالی رد می‌شود. |
| ADR-004 تماس | برخلاف عبارت «مسئول» در طرح جامع، فقط مدیر و معرف تاریخی همان عرضه مجازند. ارشد و جانشین دسترسی خودکار ندارند. نام مالک، تلفن و نشانی نیز خصوصی‌اند. |
| ADR-005 بانک مشترک | برخلاف بخش‌های «فقط ارجاع‌شده» طرح جامع، تمام اعضای فعال همان دفتر، عرضه‌های تأییدشده را می‌بینند. پیش‌نویس فقط معرف و مدیر؛ ارشد پس از ارسال برای بررسی. |
| ADR-006 تأیید | تمام عرضه‌ها تأیید لازم دارند. مدیر و ارشد مجازند؛ خودتأییدی حتی برای مدیر در این مرحله ممنوع است. استثنای مدیریتی نیازمند طراحی مستقل است. |
| ADR-007 انتشار | Property، Offering و PublicListing جدا هستند. هیچ endpoint انتشار وجود ندارد؛ تأیید فقط فعالیت داخلی است. رضایت و بازبینی عمومی در مرحله ویترین ساخته می‌شوند. |
| ADR-008 مرز دفتر در بانک | کلیدهای خارجی ترکیبی (شناسه، دفتر، مجموعه) مانع اتصال بین دفترها می‌شوند. در API نیز scope و رابطه بررسی می‌شود؛ UUID مجوز نیست. جداسازی ردیفی PostgreSQL/RLS فعلاً استفاده نشده است. |
| ADR-009 هویت عرضه | trigger بانک تغییر دفتر، مجموعه، ملک، شخص مالک و معرف تاریخی عرضه را منع می‌کند. اصلاح مشخصات شخص مجاز است؛ جابه‌جایی هویت و ادغام، فرایند آینده است. |
| ADR-010 محرمانگی | پاسخ داخلی با فهرست سفید مستقل ساخته می‌شود؛ تماس فقط از endpoint مجزا و ممیزی‌شده. جستجو فقط روی محله؛ هیچ جستجوی تلفن یا نشانی در این مرحله نداریم. رمزنگاری Fernet برای نام مالک، تلفن و نشانی در بانک. |
| ADR-011 ابطال نشست | auth_epoch عضویت در نشست ثبت می‌شود. غیرفعال‌سازی آن را افزایش می‌دهد؛ حتی فعال‌سازی دوباره نشست قدیمی را معتبر نمی‌کند. هر درخواست عضویت، حساب و دفتر فعال را دوباره بررسی می‌کند. |
| ADR-012 پول و اندازه | پول bigint صحیح تومان و API رشته عددی برای جلوگیری از افت دقت JavaScript؛ ودیعه و اجاره جدا. مساحت Decimal با دو رقم اعشار، هیچ float پولی استفاده نمی‌شود. تاریخچه قیمت append-only است. |
| ADR-013 ویرایش | نسخه اجباری + select_for_update؛ تغییر دوم 409. ویرایش مستقیم عرضه تأییدشده فعلاً ممنوع؛ بازنگری نسخه منتشرشده قابلیت مرحله بعد است. |
| ADR-014 رویداد | عامل، زمان، عملیات، شناسه و نتیجه؛ بدون کپی payload خصوصی. trigger بانک UPDATE/DELETE ممیزی و قیمت را منع می‌کند. API ممیزی فقط خواندنی و مخصوص مدیر است. |
| ADR-015 رسانه | S3 با دو bucket مستقل. مدرک فعلاً فقط JPEG/PNG واقعی تا ۸ MiB و ۲۴ مگاپیکسل؛ بازکدگذاری بدون EXIF. دانلود با مجوز تازه از خود API و بدون افشای کلید یا URL ذخیره‌ساز؛ برخلاف پیشنهاد لینک امضاشده ۵ دقیقه‌ای، لینک bearer صادر نمی‌شود. | ADR-017 منابع کارمزد | قواعد BR01 تا BR14 خوانده شده‌اند؛ هیچ نرخ نمونه یا ماژول مالی فعال نشده است. سهم تاریخی مستقل از مسئول اجرایی می‌ماند. |

## اختلاف دامنه و محدودیت‌های آگاهانه مرحله حاضر

اسناد دامنه بزرگ‌تری دارند؛ دستور فعلی آن را به مسیر کارکنان → پیش‌نویس → بررسی → بانک مشترک محدود کرده است. تقاضا، همکاری، اعلان، امور مالی، دعوت‌نامه، ویترین و OTP اجرا نشده‌اند و دکمه نمایشی ندارند.

فهرست داخلی فعلاً حداکثر ۲۰۰ نتیجه تازه با فیلتر محله برمی‌گرداند؛ صفحه‌بندی و فیلتر ترکیبی نسخه فروش در مرحله بعد لازم است. نوع ملک در enum فعلی است؛ فهرست‌های قابل مدیریت و محله‌های مجاز هنوز صفحه تنظیمات ندارند. نام، شهر و branding در بانک هستند؛ لوگو، رنگ و تماس می‌توانند در JSON تنظیمات دفتر ذخیره شوند؛ رابط فعلی نام و رنگ را مصرف می‌کند. ادعای وجود پنل کامل تنظیمات نداریم.

فرم پایه ملک شامل نوع، محله، متراژ و نشانی است؛ جزئیات اختصاصی طبقه، امکانات، وضعیت سند، قیمت توافقی و تاریخ اعتبار تکمیل نشده‌اند. اشخاص در جدول مستقل‌اند ولی مدیریت روابط متقاضی، ادغام و تشخیص تکرار شماره هنوز ساخته نشده است. مدل چند عرضه برای هر ملک را می‌پذیرد؛ API مرحله اول هر ثبت را با ملک تازه ایجاد می‌کند. پیش از افزودن endpoint عرضه مجدد، نسخه‌گذاری مشخصات ملک و مالک باید تکمیل شود.

## تصمیم‌های مرحله دوم

- ADR-019: دستور جدید مالک محصول، ادامه توسعه مرحله دوم را مجاز کرد؛ قبولی مرحله اول و آزمون یکپارچه همچنان معلق است. توسعه جدید در app مستقل crm قرار گرفت؛ جزئیات و محدودیت‌ها در phase2.md آمده‌اند.
- ADR-020: شخص و روابط چندگانه با تماس رمزنگاری‌شده و شاخص HMAC یکتای هر دفتر؛ هشدار تکرار بدون افشای هویت. ادغام خودکار داده قدیمی و تغییر شماره خارج دامنه فعلی‌اند.
- ADR-021: تماس متقاضی فقط مدیر/معرف تقاضا؛ ارجاع مسئول و شرکت در همکاری مجوز تماس طرف دیگر ایجاد نمی‌کند. متن پیگیری فقط نویسنده/مدیر و به صورت رمزنگاری‌شده است.
- ADR-022: قواعد تطبیق نسخه ۱، بدون تلورانس و تبدیل پول؛ محله ترجیحی و نوع/معامله/متراژ/بودجه الزامی. درخواست دستی ناسازگار مجاز و در رابط مشخص است. سقف فعلی بررسی ۱۰۰۰ عرضه صریح اعلام می‌شود.
- ADR-023: تقاضا و عرضه مسئول اجرایی جدا دارند؛ تاریخچه ارجاع append-only. پذیرش همکاری با معرف عرضه یا مدیر، هماهنگی بازدید با معرف/مسئول عرضه یا مدیر است.
- ADR-024: همکاری و بازدید نسخه‌دار و دارای تاریخچه غیرقابل تغییر؛ ایجاد بازدید نسخه همکاری را نیز تغییر می‌دهد. یک بازدید برنامه‌ریزی‌شده در هر همکاری؛ لغو به‌جای حذف.
- ADR-025: اعلان داخلی هم‌تراکنش با عملیات، فقط کد کنترل‌شده و UUID؛ قیود بانک کد و نوع را محدود می‌کنند. هیچ متن خصوصی در اعلان نیست. سررسیدها با پرس‌وجوی بانک نمایش داده می‌شوند؛ ارسال خودکار آینده هنوز ساخته نشده است.
- ADR-026: شخص مشترک، نسخه مستقل دارد؛ اصلاح نام از عرضه با owner_version و قفل شخص انجام می‌شود. شماره در فرم فعلاً خواندنی است تا فرایند اصلاح هویت و شاخص یکتا طراحی شود.
