# مرحله دوم — مشتری، تقاضا، تطبیق و همکاری

این مرحله با دستور «حالا مرحله دوم رو اجرا کن» روی همان مخزن ادامه یافته است. مجوز ادامه توسعه، به معنی قبولی آزمون‌های اجرا‌نشده مرحله اول نیست. این نسخه مستقل است و نام مشتری قبلی وارد محصول نشده است.

## مسیر ساخته‌شده

۱. مشاور، شخص متقاضی و تقاضای خرید یا اجاره را ثبت می‌کند، یا یک شخص از قبل مجاز را انتخاب می‌کند. شخص می‌تواند هم مالک و هم متقاضی باشد.
۲. سایر اعضای دفتر، معیارهای تقاضا را بدون نام و تماس مشتری می‌بینند. تماس فقط از endpoint جدا، برای مدیر و معرف تقاضا و با رویداد ممیزی دریافت می‌شود.
۳. تطبیق، عرضه‌های تأییدشده همان دفتر را با دلیل بررسی می‌کند. نوع ملک، معامله، بازه متراژ و بودجه الزامی‌اند؛ محله ترجیحی است. هر معیار ۲۰ امتیاز دارد و ناسازگاری الزامی امتیاز را صفر می‌کند. ودیعه و اجاره جدا هستند؛ هیچ تبدیل، تلورانس یا سرویس AI وجود ندارد. نسخه قواعد ۱ است.
۴. معرف تقاضا، مسئول اجرایی آن یا مدیر می‌تواند درخواست همکاری بفرستد. ارسال تکراری همان زوج تقاضا/عرضه، درخواست تازه یا اعلان تکراری ایجاد نمی‌کند.
۵. مدیر یا معرف تاریخی عرضه پذیرش یا رد را ثبت می‌کند؛ رد، بستن و ارسال دوباره علت کنترل‌شده دارند. هماهنگی و بازدید شماره مالک یا مشتری طرف مقابل را منتقل نمی‌کنند.
۶. پس از پذیرش، معرف عرضه، مسئول اجرایی فعلی آن یا مدیر می‌تواند بازدید آینده تنظیم کند. تغییر زمان، لغو و نتیجه با نسخه و تاریخچه مستقل ثبت می‌شوند. در هر همکاری فقط یک بازدید برنامه‌ریزی‌شده هم‌زمان مجاز است.
۷. اعضای مجاز همکاری، پیگیری و وظیفه ثبت می‌کنند. متن رمزنگاری می‌شود و فقط نویسنده و مدیر به آن دسترسی دارند. متن در فهرست یا اعلان کپی نمی‌شود. وظایف سررسیدگذشته با پرس‌وجوی واقعی بانک دیده می‌شوند.
۸. مدیر مسئول اجرایی تقاضا و عرضه را تغییر می‌دهد. معرف تاریخی و حقوق تماس ثابت می‌مانند و تاریخچه ارجاع قابل حذف یا ویرایش نیست.
۹. اعلان داخلی در همان تراکنش عملیات ساخته می‌شود؛ فقط گیرنده آن را می‌بیند و خوانده‌شدن آن را ثبت می‌کند. کد رویداد و نوع رکورد در بانک هم محدود به فهرست مجازند.

## امنیت و تصمیم‌ها

- داده‌های جدید در app مستقل `crm` قرار دارند. موجودیت Person پایه در core باقی مانده و خدمات resolution شخص در crm/people.py استفاده می‌شود.
- PersonRelation رابطه شخص با عضویت و نوع مالک/متقاضی را نگه می‌دارد؛ انتخاب UUID شخص دیگر مجوز ایجاد نمی‌کند.
- PhoneIndex از HMAC-SHA256 با دامنه اختصاصی و کلید نصب استفاده می‌کند. شماره یا digest در فهرست یا خطای تکرار نمایش داده نمی‌شود. قید یکتای دفتر/مجموعه/digest مانع ثبت هم‌زمان شخص تکراری است. ورودی فارسی/عربی یکسان می‌شود.
- تکرار متعلق به کاربر غیرمجاز فقط خطای عمومی 409 دارد؛ هیچ نام، شماره یا شناسه شخص دیگری در پاسخ نیست. مدیر یا شخص دارای رابطه می‌تواند هویت مجاز قبلی را استفاده کند.
- migration، اشخاص قبلی را index و رابطه مالک/معرف را از عرضه‌ها استخراج می‌کند. رکوردهای تکراری قدیمی خودکار ادغام نمی‌شوند و تاریخچه معرفی تغییر نمی‌کند. canonical اول برای هشدار تکرار انتخاب می‌شود؛ شخص قدیمی مجاز از فهرست اشخاص قابل انتخاب است. بررسی و ادغام اختلاف هویت هنوز فرایند آینده است.
- تغییر شماره شخص فعلاً از endpoint ویرایش عرضه مسدود است، چون باید شاخص یکتا و هویت مشترک با هم اصلاح شوند. شماره در فرم فقط خواندنی است. فرایند اصلاح شماره با بررسی هویت هنوز اجرا نشده است.
- تغییر نام مشترک شخص با `owner_version` مستقل و قفل ردیف محافظت می‌شود؛ اصلاح نام و اطلاعات عرضه در یک تراکنش‌اند. دریافت اطلاعات خصوصی `owner_version` را هم می‌دهد.
- تعلق دفتر و مجموعه تمام روابط جدید در سرور و کلیدهای خارجی ترکیبی بانک کنترل می‌شود. معرف تقاضا، هویت همکاری/بازدید و نویسنده پیگیری trigger تغییرناپذیری دارند. تاریخچه ارجاع، همکاری و بازدید append-only است.
- یادداشت خصوصی متعلق به نویسنده می‌ماند؛ از دست رفتن نقش اجرایی، آن را به جانشین منتقل نمی‌کند. مدیر مجاز است آن را با دریافت خصوصی و ممیزی ببیند.
- رابط فقط اعمال مجاز را پیشنهاد می‌کند؛ مجوز نهایی در هر درخواست سرور بررسی می‌شود. نقش/دفتر/معرف ورودی، تماس در match، متن خصوصی در notification و دسترسی خودکار ارشد ساخته نشده‌اند.
- درخواست همکاری دستی برای مورد ناسازگار مجاز است؛ رابط ناسازگاری را صریح می‌گوید. امتیاز تطبیق، پیشنهاد است و تصمیم همکاری را به‌صورت خودکار نمی‌گیرد.

## APIهای جدید

همه مسیرها زیر `/api/v1` هستند و نشست و CSRF قبلی را استفاده می‌کنند. پاسخ فهرست‌های مرحله دوم `{count, offset, limit, has_more, results}` است؛ پیش‌فرض ۳۰ و حداکثر ۱۰۰ نتیجه.

| مسیر | عملیات |
|---|---|
| people و people/{id}/private | فهرست مجاز، ثبت/استفاده مجدد شخص، دریافت تماس ممیزی‌شده |
| demands و demands/{id} | ثبت، مشاهده خلاصه و اصلاح معیارها با نسخه |
| demands/{id}/private | دریافت تماس متقاضی فقط برای مدیر/معرف |
| demands/{id}/matches | رتبه، علت، موارد ناسازگار و صفحه‌بندی |
| demands/{id}/assign و assignments | ارجاع و تاریخچه خصوصی مدیر |
| offerings/{id}/assign و assignments | ارجاع مسئول عرضه با حفظ معرف |
| cooperations و cooperations/{id} | درخواست، پذیرش/رد/بستن/ارسال دوباره با نسخه |
| cooperations/{id}/history | تاریخچه وضعیت و علت بدون متن آزاد خصوصی |
| visits و visits/{id} و history | زمان‌بندی، مشاهده، تغییر زمان، نتیجه/لغو و تاریخچه |
| followups و followups/{id}/private | پیگیری، سررسید، تکمیل با نسخه و متن خصوصی ممیزی‌شده |
| followups?due=1 | فقط پیگیری‌های باز سررسیدگذشته مجاز |
| notifications و notifications/{id} | اعلان‌های گیرنده و ثبت خواندن به‌صورت idempotent |

PATCH تقاضا، معیارهای کامل فرم و `version` را دریافت می‌کند؛ هویت شخص و معرف از این مسیر قابل تغییر نیست. تعیین مسئول به‌صورت عملیات مجزای مدیر انجام می‌شود. بستن همکاری تا تعیین تکلیف بازدید برنامه‌ریزی‌شده رد می‌شود. بسته‌بودن تقاضا، match و بازدید تازه را مسدود می‌کند؛ لغو/ثبت نتیجه بازدید موجود برای حفظ سابقه ممکن است.

## اجرا و داده نمونه

نصب تازه:

```bash
python3 infra/init_env.py
docker compose up --build -d
docker compose logs migrate storage-init
docker compose run --rm backend python manage.py seed_demo
docker compose run --rm backend python manage.py seed_crm_demo
```

seed_demo رمزهای تصادفی حساب‌ها را فقط هنگام اجرا نشان می‌دهد. seed_crm_demo رمز تازه نمی‌سازد؛ روی حساب‌های همان دفتر نمونه، عرضه تأییدشده، تقاضا، همکاری پذیرفته، بازدید آینده و پیگیری کاملاً ساختگی می‌سازد. اگر رکورد کاری از قبل وجود داشته باشد، برای جلوگیری از بازنویسی/تکرار متوقف می‌شود. شماره‌ها صرفاً داده آزمایشی‌اند و هیچ پیامکی ارسال نمی‌شود.

ارتقای نسخه اولِ دارای داده، در محیط آزمایش و پس از backup با حفظ همان .env و کلید رمزنگاری:

```bash
docker compose build
docker compose run --rm migrate
docker compose up -d
docker compose logs migrate storage-init
```

env را دوباره تولید نکنید؛ شاخص اشخاص موجود به کلید نصب وابسته است. seedها روی بانک عملیاتی یا بانک غیرخالی اجرا نشوند. قبل از داده واقعی، migrations باید روی کپی پشتیبان آزمایش و صحت دسترسی تماس کنترل شود.

آزمون یکپارچه در محیط دارای Docker:

```bash
sh infra/verify.sh
```

این اسکریپت build رابط، migration واقعی، init ذخیره‌ساز، check و آزمون‌های core و crm را با S3 واقعی اجرا می‌کند. اجرای آن در محیط فعلی ممکن نبود؛ وجود اسکریپت به معنی قبولی آزمون‌ها نیست.

آزمون‌های مستقل:

```bash
docker compose run --rm backend python manage.py test core.test_validation crm.test_rules --noinput
```

## سناریوی دستی

در سه نمایه جدا با manager،advisor1 و advisor2 وارد شوید. advisor1 عرضه را ثبت و manager تأیید کند. advisor2 تقاضا و match را بسازد و درخواست همکاری بفرستد. advisor1 درخواست را بپذیرد و بازدید ثبت کند؛ advisor2 زمان شمسی را بدون تماس مالک ببیند. متن پیگیری advisor2 برای advisor1 قابل دریافت نباشد. manager ارجاع را تغییر دهد؛ جانشین همچنان تماس مالک/متقاضی را نگیرد. بازدید جابه‌جا/لغو یا تکمیل شود و تاریخچه باقی بماند. اعلان هر کاربر فقط در صندوق خودش دیده و خوانده شود. نشست مشاور غیرفعال در همه مسیرهای جدید رد شود.

## محدودیت‌های باقی‌مانده

- PostgreSQL، S3 و مرورگر این مرحله در محیط حاضر قابل اجرا نبودند؛ پذیرش یکپارچه دو مرحله همچنان باز است.
- match فعلاً ۱۰۰۰ عرضه تأییدشده با ترتیب پایدار را ارزیابی می‌کند و سقف در پاسخ اعلام می‌شود؛ بهینه‌سازی برای تمام بانک بزرگ و آزمون بار باقی است. فیلتر امکانات و تعداد اتاق به تکمیل مدل ملک وابسته است.
- انتخاب شخص موجود در فرم از ۱۰۰ شخص مجاز تازه است؛ صفحه اشخاص صفحه‌بندی دارد. انتخاب‌گر جستجوی پیشرفته شخص و فرایند ادغام/اصلاح شماره باقی است.
- ورودی زمان از کنترل مرورگر با تاریخ میلادی و ساعت صریح تهران گرفته می‌شود؛ نمایش ذخیره‌شده شمسی/تهران است. تقویم ورودی شمسی اختصاصی هنوز ندارد.
- یادآوری پس‌زمینه، مهلت کاری خودکار و پیامک ساخته نشده‌اند. نمایش سررسیدگذشته و اعلان رویداد همان لحظه عملیاتی‌اند؛ ارسال زمان‌بندی‌شده ادعا نمی‌شود. Celery/Redis هنوز اضافه نشده‌اند.
- بستن/بازکردن تقاضا باید توسط معرف یا مدیر انجام شود؛ بستن تقاضا، سوابق همکاری/بازدید را پاک نمی‌کند.
- مالی، انتشار عمومی، سازندگان، خرید آپدیت و مدیریت عملیاتی چنددفتره خارج این مرحله‌اند.
